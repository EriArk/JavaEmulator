# Hardware shading and pipeline specialization, 2026-10-13

Research branch only. No production engine/license switch, public APK, private
engine source or game archive is included in this checkpoint.

## Changes

- Flat and two-sided lighting now run on the indexed hardware geometry path.
  Flat colors use the third vertex, including when clipping removes that vertex.
  Two-sided lighting computes front/back colors separately and chooses the side
  per primitive. Culling, reversed winding, mirrored transforms, material color
  tracking, local camera lighting, alpha, textures and fog remain supported.
- Corrected an inherited unlit-flat defect: vertex colors were interpolated
  without a material/normal array. The guarded CPU adaptation and the new GPU
  path both use the third vertex's color/alpha before clipping. Exact expected
  RGB/RGBA tests cover CPU, prepared GPU and hardware GPU independently.
- GL front-face convention stays fixed; the M3G winding is applied explicitly
  to the cull side and front/back color selection. This fixes incorrect back
  lighting on the Phone emulator without a renderer-name/device workaround.
- Immutable light, material, matrix and texture-transform snapshots reuse
  unchanged uniform groups within an uninterrupted submission. A program switch,
  CPU barrier or context recovery starts with a complete state setup.
- Split ordinary and extended-lighting shaders into two context-owned programs.
  The extended program is compiled once when first needed and reused. Ordinary
  geometry and sprites keep the original, smaller varying interface. Switching
  programs resets uniform reuse, preserving texture/fog/mask/depth state.
- Oversized transient meshes no longer evict reusable small resident meshes.
  Shrinking/disabling the cache still enforces its byte limit.

The original EPL polygon-mode implementation was read for its hardware-state
approach, not copied. The independently written GLSL follows the published
[M3G PolygonMode contract](https://nikita36078.github.io/J2ME_Docs/docs/jsr184/javax/microedition/m3g/PolygonMode.html)
and the third-vertex provoking convention in
[OpenGL ES 3.0](https://registry.khronos.org/OpenGL/specs/es/3.0/es_spec_3.0.pdf).
No original-engine implementation or licensing notice was removed.

### Phone Portability Diagnosis

SwiftShader's translated GLES path returned inconsistent `gl_FrontFacing`
results after changing the GL winding convention. The same tests passed on
Adreno. A fixed GL convention with explicit M3G side selection fixes this
observed behavior; no particular upstream defect location is asserted.
[Reproduction before the fix](lighting-20261013/phone-before-fix.txt).

The remaining combined texture/fog/alpha comparison differed on 168 samples
along one-pixel nearest-texel boundaries, not across the lit surfaces. Geometry
placed the transition almost on a pixel center, making subpixel rounding visible
between homogeneous and CPU-prepared vertices. The fixture now offsets its
textured geometry slightly away from that unstable boundary; its error/count
tolerances are unchanged. An additional independent test checks exact RGB texels
across both paths with flat/two-sided shading. This does **not** establish exact
cross-path boundary selection on every driver.
[Diagnostic](lighting-20261013/phone-texel-boundary-diagnostic.txt),
[prepared image](lighting-20261013/lighting-texture-expected.png),
[hardware image](lighting-20261013/lighting-texture-actual.png).

## Performance

Control: preceding indexed GPU APK (`0697d76c` implementation), using the same
benchmark scenarios and settings as the candidate. GPU geometry, mesh residency
and released-depth discard are enabled on both. Each fixture uses 512 warmup
frames followed by five batches of 32 frames. All benchmark APK hashes and raw
per-batch timings are retained; these are synthetic costs, not real-game FPS.

Means across two control and two specialized-shader Retroid runs before the
portable facing correction, milliseconds per frame:

| Fixture | Size | Before | Final | Reduction |
| --- | --- | ---: | ---: | ---: |
| Dense flat lighting | 240x320 | 4.020 | 1.906 | 52.6% |
| Dense flat lighting | 320x240 | 4.895 | 1.821 | 62.8% |
| Alternating front/back lighting | 240x320 | 4.209 | 2.055 | 51.2% |
| Alternating front/back lighting | 320x240 | 5.071 | 1.918 | 62.2% |

The four new fixtures use 672 hardware draws, one retained mesh upload and no
prepared-geometry upload each. Previously they transformed/lit geometry on the
CPU and streamed prepared triangles. Uniform reuse reduces GL commands but does
not establish an across-the-board frame-time improvement: unchanged fixtures
range from 2.6% faster to 3.5% slower in these runs. Multi-object/material cases
remain 2.2-2.9% slower, so zero performance regression is not claimed.

An intermediate combined shader increased ordinary-scene wall costs while CPU
times stayed similar. Shader specialization removed most of that overhead;
the intermediate result is retained, not substituted with a passing run.

## Image Comparison

The previous 30 fixtures remain pixel-identical to the control in both final
runs. The four newly accelerated lighting fixtures are **not** pixel-identical.
Most channel errors are within 4 levels, with a maximum of 6 for landscape flat
lighting. The candidate CPU uses approximate inverse-square-root/reciprocal
lighting calculations, whereas the shader uses GPU arithmetic. These differences
are not hidden behind a broad visual-equivalence claim.

The landscape two-sided fixture also differs at one high-contrast stripe-edge
sample `(152,134)`: old RGB `(156,137,116)`, new `(7,7,7)`, maximum error 149.
Only one of 76,800 pixels exceeds 8 channel levels. Exact cross-path edge
selection is not guaranteed; this is explicitly retained as a parity limit.

[comparison 2, including >8/>32 counts](lighting-20261013/comparison2.json),
[intermediate comparison](lighting-20261013/initial-comparison.json).

After the portable facing correction, **all 34 fixtures are pixel-identical to
the preceding specialized shader**, not to the older CPU-lighting control.

## Remaining Boundary

Depth-offset geometry still uses CPU preparation with GPU rasterization to
preserve the candidate's signed-depth behavior. CPU posing, unsupported-state
fallback and the LCDUI bitmap color-transfer boundary remain. The extended shader
still has first-use compilation cost. This batch does not establish native-engine
performance parity, broad GPU-driver coverage, audio quality, physical-control
ergonomics, a full playthrough or readiness to replace the production engine.
Live GitHub releases were not rechecked and no release was created.
